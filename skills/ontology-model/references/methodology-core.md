## 1. S1 知识萃取

### 1.1 三维访谈提问清单（骨架）

- 对象维（映射 SKOS/RDF/OWL）：业务里有哪些需要独立管理的对象？每个对象靠什么唯一标识？各有哪些属性、取值范围是什么？哪些术语存在「同词不同义 / 同义不同词」？每个概念的首选名称与别名分别是什么？（KC-20261013-007）
- 任务维（映射 OWL-S/SPARQL）：完整业务流程分哪几步？步骤间的时序约束是什么？每步的输入、输出、前提、效果各是什么？异常如何处置？哪些环节需要查询哪些信息？（KC-20261013-007）
- 规则维（映射 SWRL/OWL/ODRL）：有哪些判断条件？模糊经验（「这类情况一般不通过」）能否转成量化阈值？哪些是刚性红线、哪些只是建议？哪些角色可以 / 须经确认 / 禁止执行哪些动作？（KC-20261013-007）

### 1.2 萃取纪律

- 隐性知识不靠自由访谈，靠上述三维提问清单系统化萃取；协议产出物 = 标准化描述句（供 S2 组装），仍须过 G1 准入评审才可入模。（KC-20261013-007）
- 三维是提问框架不是本体结构：对象维不只产出对象类构件，规则维的访谈常反向补全对象属性——萃取时允许跨维回填。（KC-20261013-007）
- 访谈对象须是「做决策的人」而非「管流程的人」；事理层知识要求可登记来源与专家复核记录。（KC-20261013-007，KC-20261013-001）
- 强模糊判断（纯直觉式表述）不可直接形式化，须先经规则维提问逼出量化阈值；逼不出阈值的登记「待确认项」，不入模。（KC-20261013-018，KC-20261013-007）
- 访谈引导用三层框架：从具体现象提炼本质结构（抽象化）→ 让隐性经验可传递、模糊判断可追溯（结构化）→ 让模型可持续迭代（进化性）。（KC-20261013-002）

## 2. S2 语义原料组装

### 2.1 七类语义 × W3C 标准映射（完整性过筛 checklist）

| 语义类 | 绑定标准 | 承载内容 |
|---|---|---|
| 对象描述 | RDF/OWL/SKOS | 概念、属性、术语首选/替代标签 |
| 分层约束 | OWL | subclassOf、等价类、不相交 |
| 控制规则 | SWRL | 条件判断、量化阈值触发 |
| 流程活动 | BPMN2.0+OWL-S | 流程时序、动作 IOPE（输入-输出-前提-效果） |
| 权限管控 | ODRL | 自主/人工确认/禁止三类行为边界 |
| CRUD 查询 | SPARQL | Agent 自主取知接口 |
| （+1）目标与评估 | — | 声明本本体服务的消费场景，防模型与业务目标脱节 |

（KC-20261013-005）

- 七类是完备性 checklist 而非强制全建：按场景裁剪，但每个裁剪决策须显式登记——缺哪类语义层 = 已知风险。（KC-20261013-005）
- 「+1」目标评估不可省：它是防「本体博物馆」的框架级保险，也是 S4 业务贴合度审计与 S6 验收的基准锚点。（KC-20261013-005，KC-20261013-004）
- 流程活动类构件必须带 IOPE 四要素；关键不在明确输入输出，而在补全「前提+效果」——这是流程能反映业务时序动态变化的核心。（KC-20261013-005，KC-20261013-023）

### 2.2 七类描述句式（NL→构件转译模板）

- 对象描述 → DataProperty 句式：「X 具有属性 Y，取值范围为 Z」。（KC-20261013-006）
- 分层约束 → subclassOf/Constraint 句式：「所有 A 都是 B」「A 与 B 不相交」。（KC-20261013-006）
- 术语 → EquivalentClass/SKOS 句式：「X 又称 Y，首选标签为 Z」。（KC-20261013-006）
- 控制规则 → SWRL Rule 句式：「若条件 C 满足，则触发结论 R」，必须含量化阈值。（KC-20261013-006）
- 流程活动 → Process 句式：「步骤 S 的输入/输出/前提/效果」。（KC-20261013-006）
- 权限管控 → Policy 句式：「角色 R 可以 / 须经确认 / 禁止执行动作 A」。（KC-20261013-006）
- CRUD 查询 → SPARQL 查询模板句式。（KC-20261013-006）
- 记法纪律：描述句以七类语义为纲组织；「29 句」是该框架的总称（来源文献图 6-1 为 7 类合计 29 子项，2026-11-10 按原书图核对确认）。本管线模板 `assets/tpl-29-sentences.md` 的子项表为**编译导向重构**——子项按 NL→W3C 构件映射需要扩展重排（如控制规则类由「触发规则」1 项扩为触发/优先级互斥/处置动作 3 项），子项编号以模板自身体系为准，不硬引来源文献编号。（KC-20261013-006）

### 2.3 最小化双原则（操作判据）

- 范围原则：本体构建范围由 AI 业务意图目标决定，「够用且可扩展」——只建当前意图所需构件，描述集只写意图范围内的业务。（KC-20261013-008，KC-20261013-006）
- 构件/字段准入判据一问：「哪个 Agent 任务的哪个环节消费它？」答不出即登记不建——进缓建清单留痕，不是丢弃。（KC-20261013-008）
- 「够用」的判据主体是业务意图而非建模者审美；意图变更时范围随之重裁。（KC-20261013-008）
- 表达极简 ≠ 省略量化阈值：删的是修辞冗余，不是逻辑精度。「指标值＞85% → 风险等级+1」不得简写为「指标偏高会增加风险」。（KC-20261013-008）
- 「可扩展」的结构保证 = 分层架构预留扩展点（见 §4.3）；无扩展点的最小化 = 一次性本体。（KC-20261013-008，KC-20261013-015）

### 2.4 点-线-面小切口（范围策略）

- 反模式禁令：拒绝「大而全」顶层设计——一次性全域建模投入大、周期长、消费稀薄，是本体博物馆的直接成因。（KC-20261013-016，KC-20261013-004）
- 「点」的选择判据：高价值 / 高频 / 高风险决策场景，且可闭环、可评估。（KC-20261013-016）
- 点阶段 MVP 四步：精准定义场景 → 快速构建本体与数据管道 → 开发轻量智能应用 → 闭环验证与迭代。（KC-20261013-016）
- 线（纵轴领域拉通：实例层关联→领域层统一→公共层对齐→动作层标准化）与面（横轴跨域桥接：识别交互点→语义映射→桥接本体+联邦查询）的启动前置 = 点阶段黄金用例达标；未验证先拉通是反模式。（KC-20261013-016，KC-20261013-015）
- 横轴五难题应对：概念冲突 → SKOS 跨领域术语映射+桥接属性 / 粒度差异 → 多粒度建模+聚合规则 / 动态交互点 → 高频跨域场景逆向识别+治理委员会定期评审 / 规则冲突 → 桥接本体优先级或上下文约束+SWRL 冲突消解 / 自主性↔互操作性 → 联邦式集成。（KC-20261013-016）
- 纵轴三难题应对：概念异构 → 领域术语词典（SKOS 首选/替代标签）+同名异义界定上下文并拆分概念 / 规则冲突 → 优先级机制+互斥规则+SWRL 冲突消解 / 扩展性 → 分层架构下新增只加实例。（KC-20261013-016）
- 联邦式集成不强制合并：各领域本体保留自主权，经顶层核心本体对齐 + 映射文件交互；桥接本体与映射文件本身也须过治理。（KC-20261013-016）
- 首期范围只做「点」；线/面显式后置登记。（KC-20261013-016）

## 3. G1 准入评审

### 3.1 四标准判定问句（逐句标注通过/存疑）

- 描述清晰：不懂本行业的读者读这句话是否只有一种理解？有无未定义的指代、多义词、模糊限定（「一般」「原则上」）？（KC-20261013-011）
- 逻辑正确：规则的条件与结论是否自相矛盾？同类多条规则之间是否冲突？分层约束是否违反业务常识（如把互斥概念写成父子类）？（KC-20261013-011）
- 内容完备：该类语义的要素是否齐全——规则句是否有条件、阈值、结论三段？流程句是否有 IOPE？权限句是否明确角色与动作？（KC-20261013-011，KC-20261013-006）
- 极简表达：这句还有没有可删的修辞冗余？（删冗不删阈值，判据见 §2.3）（KC-20261013-011，KC-20261013-008）

### 3.2 两段评审分工

- 初审（建模工程师/模型驱动）：Checklist 式语义规范性检查——句式合规、术语一致、W3C 标准映射正确。（KC-20261013-011）
- 复核（业务专家驱动）：复核会议验证业务规则闭环与内容完备性——业务语义正确性只有专家能判。（KC-20261013-011）
- 两段不可互相替代：工程师判不了业务对错，专家判不了句式合规。（KC-20261013-011）
- 评审对象是自然语言描述句，不是 OWL 模型——模型层测试属 S6 黄金用例环节，两道闸阶段不同勿混。（KC-20261013-011，KC-20261013-014）

### 3.3 测试–增强循环（有可执行测试手段时）

- 知识层预验证：用可执行测试（识别/查询）暴露知识区分不足 → 补精细规则与行为逻辑 → 再测至稳定；在描述句阶段即跑「用得上吗」的实证检验。（KC-20261013-011）
- 无可执行测试手段的纯静态描述集只过四标准，测试–增强循环不适用。（KC-20261013-011）

### 3.4 复核段强化判据（企业环境实践增补）

- 三层确认结构：①AI 辅助确认层先行——双模型/推理机校验先收敛形式与一致性问题；②专家裁定层——专家只裁关键口径冲突与业务语境下明显反常的设定，不做全量复核；③易审核性前置——专家裁定的前提是「审得动」（呈现形态见 §6.3）。（KC-20261013-011）
- 多立场交叉验证：单专家裁定有立场偏置风险；用不同立场的专家三角化（如产品侧专家 × 一线业务专家 × 系统侧专家各审本立场熟悉的维度）抵消单立场偏置。（KC-20261013-011）
- 闸门后置警戒：两段评审审的是描述集内部一致性；业务实践偏差与立场偏置属「文档闸门审不出」的缺陷类别，须由多立场复核 + S6 真实数据对照兜底——G1 通过不代表业务口径无虞。（KC-20261013-011）

## 4. S3 生成

### 4.1 语义编译官定位与只读不写

- LLM 已内化 W3C 语义栈语法，建模瓶颈从「写语法」转向「定义业务逻辑」；生成环节 = 把描述集+词典直译为本体模型的语义编译，不是自由创作。（KC-20261013-010）
- 输入三要素缺一不可：描述句集 + 业务术语词典 + Prompt（角色/输入/输出格式/质量规范四段式）。（KC-20261013-010）
- 只读不写工作流：专家全程不手工「写」模型，只「读」生成物并迭代自然语言描述；对生成物的意见一律走缺陷/仲裁通道，不直接改稿。（KC-20261013-010）
- 反模式禁令：编译官不自带正确性保证——生成物必须过质检（双模型+专家把关+黄金用例）才可交付。（KC-20261013-010）
- 工具口径：优先 W3C 标准（AI 已内化其语法）；Protégé 类工具仅作导入验证器，不作主建模工具。（KC-20261013-010，KC-20261013-019）

### 4.2 模型选型五维验证（换模型/接新模型时实测）

- W3C 标准理解力 → 本体转译测试；语义逻辑推理 → 隐性关系推导；模式合规性校验 → 反例识别；多层级语义对齐 → 层级分类测试；领域知识覆盖 → 领域术语库对齐。（KC-20261013-010）
- 能力准入底线测试：输出含 rdf/owl 等命名空间且能被本体工具导入解析，方证明模型已掌握 W3C 语义规范。（KC-20261013-010）
- 通用对话能力榜单不能替代上述实测。（KC-20261013-010）

### 4.3 分层架构（可扩展的结构保证）

- 三层划分：公共层（跨域通用概念：时间/地点/事件/参与者）→ 领域层（领域共性：产品族/类别族）→ 实例层（具体个体）；流程构件另归动作层成四层口径——两种口径历史并存，产出物中注明本次采用三层还是四层口径。（KC-20261013-015）
- 扩展机制判据：新增产品/对象只需「领域层加子类 + 实例层加实例」而无须重构模型——做不到即分层失败。（KC-20261013-015）
- 分层收益在「多实例复用」：单实例场景强分层 = 过度设计。（KC-20261013-015）
- 公共层优先对齐行业级标准本体（如金融业的 FIBO）而非自建——有行业级本体可用时不重复造轮子。（KC-20261013-015，KC-20261013-003）
- 动作层构件与「7+1」流程活动类语义对应，须带 IOPE 四要素。（KC-20261013-015）

### 4.4 要素设计四规则与多本体划分

- 对象按独立业务实体拆分，判据 = 是否有独立生命周期与标识；防「一个大类包打天下」与「每属性一个类」双向失控。（KC-20261013-019）
- 关系绑定具体业务动作：关系命名动词化、可推理（用「申请/审批/核销」式动作动词，禁用「持有/关联」式笼统动词）。（KC-20261013-019）
- 规则与对象解耦：规则可多对象复用，触发条件在本体中定义；跨领域复用规则须过语义一致性检查——同名规则在不同本体的阈值可能不同。（KC-20261013-019）
- 流程经本体结构化预设：流程即约束，避免大模型不受约束的推理。（KC-20261013-019）
- 多本体划分判据：按「可闭环、可评估、可替代人工」的 Agent 任务划分；本体间可合并和复用。（KC-20261013-019）

### 4.5 消费链路绑定（反博物馆）

- 立项/生成闸门三问：这个本体能否触发行动？能否给出因果链？能否被 Agent 调用？任一为「否」即不立项。（KC-20261013-004）
- 验收判据：逐对象/逐规则检查消费链路挂载率——每个构件必须能指出「哪个 Agent 任务在哪个环节调用它」。（KC-20261013-004）
- 定位铁律：本体是为 AI 服务的语义基础设施，Agent 才是价值创造的执行者；禁止把本体当独立数据库建设。（KC-20261013-004）
- 反面镜像：规模再大、不绑定消费场景的本体 = 陈列满分、实战为零。（KC-20261013-004）

### 4.6 多源整合与规则公理化

- 语义标准化映射：自然语言需求表述与规格参数建立双向可译的精准映射。（KC-20261013-018）
- 多源连接不重构：多源数据经声明/视图/链接关联引用，不搬迁、不重构源系统。（KC-20261013-018，KC-20261013-020）
- 规则公理化：把散落在文档与硬编码里的业务规则抽为本体公理——规则可审计、可复用、可推理。（KC-20261013-018）
- 公理化前提：规则可形式化；强模糊判断须先过三维访谈萃取阈值（见 §1.2），不可直接公理化。（KC-20261013-018）
- 注入侧 Token 超长三对策：渐进式技能调用 / 上下文压缩 / 多轮对话拆分。（KC-20261013-018）

## 5. S4 质检

### 5.1 双模型角色与选型判据

- 单一大模型难以兼顾逻辑生成与严苛审校（同模型自检有确认偏误）——生成者 A 与审计者 B 必须异构。（KC-20261013-012）
- A（生成者）选型：长上下文、创意高，负责生成/修订模型与辩护。（KC-20261013-012）
- B（审计者）选型：推理严密、指令遵循极高、具黑盒测试思维，专职挑错；创意型模型不适合当 B。（KC-20261013-012）
- 与机械校验互补不替代：推理机/脚本查形式矛盾，双模型查语义贴合与业务逻辑漏洞。（KC-20261013-012）

### 5.2 审计维度与裁定规则

- B 审计三维度：语法规范性 / 逻辑一致性 / 业务贴合度；输出四元组「严重级别–问题描述–本体位置–修改建议」。（KC-20261013-012）
- 闭环流转：生成 → 审核 → A 对每条缺陷辩护或修订 → 多轮博弈收敛。（KC-20261013-012）
- 仲裁裁定规则：A/B 结论一致（审计通过或辩护全部成立）→ 自动通过；对核心规则产生争议 → 升级人工终审，专家只处理争议项、不做全量审查。（KC-20261013-012）
- 硬禁令：核心规则争议不可由第三个模型裁决——机器仲裁机器争议在核心规则上不合法。（KC-20261013-012）
- 业务贴合度审计的基准 = 描述句集 + 术语词典 + 目标评估（消费场景登记）；基准缺失时该维度须显式声明降级口径，不得以「无基准下皆自创」的机械推论充数。（KC-20261013-012，KC-20261013-005）
- 规范对齐维度判定依据：按 §2.1 映射表逐类核对——建了哪类语义，就核对该类绑定的 W3C 标准用得对不对。（KC-20261013-005）

## 6. S5 结构把关

### 6.1 三步审图

- 第一步·全局拓扑：看整体分类结构——检查分类不当（应为不相交类却被并列/混淆）、孤岛概念、层级失衡。（KC-20261013-013）
- 第二步·局部语义穿透：对关系做 OWL 四属性校验（业务语义问句见 §6.2）。（KC-20261013-013）
- 第三步·规则路径回溯：沿 SWRL 触发链与 IOPE 匹配回溯规则路径；典型缺陷模式 =「单事件即触发」——只感知单一信号就出结论，须补前置核验节点与阈值判定节点，改单触发了多维约束闭环。（KC-20261013-013）
- 工具无关性：三步法可脱离专业 OWL 工具执行（文本拓扑报告对照清单即可）；先把审查项清单化，可视化工具只是效率增益。（KC-20261013-013）
- 边界：三步法聚焦结构与逻辑；业务语义正确性靠 G1 专家复核与 S6 黄金用例，S5 不越权代判。（KC-20261013-013）

### 6.2 四属性业务语义问句

- FunctionalProperty：「业务上一个该类实例，此属性是否只能有一个值？」是 → 应声明函数属性；违反唯一性的建模是缺陷。（KC-20261013-013）
- InverseFunctionalProperty：「此属性的值能否在全业务范围内唯一反推出主体？」是（如全局唯一标识）→ 应声明反函数属性。（KC-20261013-013）
- TransitiveProperty：「A 对 B 有此关系、B 对 C 有此关系时，业务上 A 对 C 是否必然成立？」是 → 声明传递属性并检查层级链是否补全。（KC-20261013-013）
- inverseOf：「正向关系成立时，逆向是否必然存在对应事实？」是 → 声明逆属性对，检查双向闭环无断链。（KC-20261013-013）
- 四检查通用于任何 schema（含 ERD 与卡片关系网），不限 OWL 载体。（KC-20261013-013）

### 6.3 易审核性两级阶梯（专家把关的前置条件）

- 报告级可审：把人可读审计报告（四元组缺陷单等）呈现给人复核。局限：TTL/OWL 对业务专家不可读，此级只对「强工程认知的业务负责人」类混合角色有效——审核能力单点依赖混合角色，不可规模化。（KC-20261013-013）
- 图示级可审：图形化交互浏览（点选对象、图示属性关系、标记异常），不具备工程能力的专家也能定位关注点——此级落地后三步法才能真正交给普通业务专家执行。（KC-20261013-013）
- 诊断判据：只有报告级而无图示级时，专家把关实质由混合角色代偿——这是「易审核性未闭合」的典型信号，应在交付/复盘中登记。（KC-20261013-013）

### 6.4 入库形态与运维参考（MVP 外延要点）

- 存储演进：初期文档存储（TTL/MD + Git 式版本控制）即可，规模化后再升级图数据库/本体库；「规模化」触发条件须落地时自定义（查询并发/构件数/加载延迟阈值）。（KC-20261013-020）
- 文档存储期的版本与权限纪律不能省：从第一天执行，否则升级图库时资产不可迁。（KC-20261013-020）
- 一致性校验按语义类对应：结构（OWL/RDF）、概念（SKOS）、规则（SWRL）、流程（OWL-S）、权限（ODRL）、事件逻辑六类——建了哪类语义就校验哪类，可降级为治理 checklist。（KC-20261013-020）
- 入库审查五类（作交付验收参考）：材料完备性 / 语法与结构 / 元数据规范 / 质量证明（含问题关闭率）/ 安全与合规。（KC-20261013-020）

## 7. S6 业务验收

### 7.1 黄金用例设计判据

- 用例三元组：测试场景 + 必须能回答的核心问题 + 预期结果；由专家基于核心流程/决策点/典型异常编写。（KC-20261013-014）
- 判据主体是业务问题而非形式指标：「必须能回答的核心问题」写不出来 = 消费场景未定义，回查立项闸门三问（§4.5）。（KC-20261013-014，KC-20261013-004）
- AI 扩展矩阵：以黄金用例为种子，由模型自动扩充边缘/异常/压力用例——专家守核心路径，AI 铺覆盖面。（KC-20261013-014）
- 测试四价值：业务覆盖度量化 / 成熟度量化 / 可回归资产 / 注入边缘异常暴露隐患。（KC-20261013-014）

### 7.2 失败归因判别（先归因后修，禁止盲改）

- 判别法 = 描述集回溯：把失败用例的预期结果逐句回溯到描述句集。（KC-20261013-014）
- 描述集有对应描述句、本体未正确体现（构件缺失/关系方向错/阈值错）→ 模型缺陷，回生成环节修模型。（KC-20261013-014）
- 描述集无此规则、预期结果系测试时补充 → 用例错误（修用例）或语义原料缺口（登记后回 S2 补描述句、重过 G1），二者按补充内容是否成立区分。（KC-20261013-014，KC-20261013-011）
- 本体中两条公理/规则可分别推出相反结论 → 规则冲突，升级人工仲裁。（KC-20261013-014，KC-20261013-012）
- 通过率阈值须按领域风险重定（来源案例参考阈值：80% 达标、迭代一周收敛 90%）：高合规场景阈值应更高，不照搬案例数字。（KC-20261013-014，KC-20261013-028）

### 7.3 穿刺式验证（低成本路线验收，S6 的轻量化变体）

- 定位判据：穿刺验证的对象是「本体增强 Agent 这条技术路线是否走得通」，不是产品可用性——穿刺通过 ≠ 可规模化，后续仍走点-线-面。（KC-20261013-028）
- 组织形态：精干四角色端到端穿透全链（业务数据专家 / 本体工程师 / AI 工程师 / 项目经理——严控验证周期与范围，锁定目标不扩散，协调资源、清除外部阻碍）。（KC-20261013-028）
- 范围纪律：仅搭建验证必需的核心本体，「手工作坊」方式快速成型，拒绝过度工程化与冗余设计。（KC-20261013-028）
- 量化证据三重：小样本真实需求 + 明确阈值 + 迭代增速。（KC-20261013-028）
- 硬禁令：穿刺产物不可直接进生产——手工作坊刻意牺牲工程质量换验证速度，转正须按完整管线重建，防验证资产带病转正。（KC-20261013-028）

## 8. 消费侧设计要点（S3 扩展位：消费链路登记的设计依据）

### 8.1 三段式能力（业务 Agent 验收框架）

- 明事实：Agent 经 SPARQL 等接口从本体库自主获取业务状态与所需本体切片；动态事实关联三能力管线=数据摄取→语义映射→关系构建，把零散异构事实数据整合为「所见即所知」的实时上下文。（KC-20261013-023，KC-20261013-005）
- 懂事理：SWRL 规则判断 + OWL-S 行动规划；动作原语设计的关键在补全「前提+效果」，不止输入输出。（KC-20261013-023，KC-20261013-005）
- 会行动：工具调用 + ODRL 三类行为边界（自主执行 / 须人工确认 / 禁止）逐动作定权限；动态 Action 两机制=执行前多重校验（合规/可行/安全，任一失败不发且触发告警或替代方案）+执行后状态回传（成功/失败/异常码→重试/降级/终止）。（KC-20261013-023）
- 验收判据：三段完备性作业务 Agent 验收框架——只会问答 = 明事实层残缺；本体缺位时 Agent 退化为静态知识切片问答。（KC-20261013-023）

### 8.2 意图-本体对齐

- 意图拆解三步：明确业务目标 → 拆解子意图 → 优化颗粒度。（KC-20261013-024）
- 意图设计三原则：聚焦（单一核心功能，明确专属角色与任务边界）/ 独立（相互独立、无交叉重叠、无功能冗余）/ 适配（适配 Agent 技术能力与应用场景，兼顾本体加载与任务执行需求）。（KC-20261013-024）
- 对齐三范式（硬编码映射 → 规则引导语义映射 → 本体自主推理对齐）是演进方向不是越高级越好：意图稳定、切片少的场景固定映射最经济；范式升级触发 = 映射表维护成本超过收益。（KC-20261013-024）
- 失准双后果：意图过粗 → 本体调用泛化引入噪声；过细 → 对齐难度与维护成本激增。（KC-20261013-024）
- 对齐表是活资产：「对齐–执行–评估–修正」循环，执行偏差回流修正映射。（KC-20261013-024）

### 8.3 约束强度分级

- 强弱判据：决策失误的后果不可逆性与合规刚性——涉安全合规 = 强约束，建议类 = 弱约束。（KC-20261013-025）
- 建模落法：约束等级是规则构件的一等元数据字段，不是文档注释——标准化、可配置、可解释。（KC-20261013-025）
- 消费机制：强约束不可被推理覆盖（硬门禁，违反即拦截）；弱约束可被上下文证据加权调整（软参考）。（KC-20261013-025）
- 等级可配置：同一规则在不同场景可升降级，配置变更走版本治理；复杂场景可扩三档（禁止/须确认/自主），与 ODRL 三类行为边界对齐。（KC-20261013-025）

### 8.4 按风险定介入

- 决策→行动转化三模式：指令直驱（须同时满足「明确规则、低风险、后果可控」三原则）/ 人机协同确认 / 业务协同执行型（多 Agent 协同：主 Agent 高层决策 → 子 Agent 跨系统、多角色联动执行）。（KC-20261013-026）
- 介入三档：低风险 = 负责人一键确认；中风险 = 填写简要确认理由；高风险 = 触发专家会审。（KC-20261013-026）
- 反过度介入原则：「该介入时必介入、无须介入时不干预」——档位以风险为唯一判据，介入本身有成本。（KC-20261013-026）
- 联动判据：强约束规则关联的动作默认中/高风险档。（KC-20261013-026，KC-20261013-025）
- 介入反馈闭环：修正意见、确认理由、会审结论须留痕并回流为「本体优化建议」——无留痕则闭环断裂，介入退化为纯人工成本。（KC-20261013-026）
- 业务协同执行型细则：协同四原则=场景适配/权责清晰/交互统一（本体定义+执行事件总线）/闭环优化；四步联动=决策拆解→指令下发→联动执行→反馈优化。（KC-20261013-026）

### 8.5 表示–推理–验证三阶段增强

- 表示阶段：本体补业务概念与关系的形式化表示（业务常识）；推理阶段：在本体约束的行为边界内生成；验证阶段：对结论结合行动效果做合理性、一致性与合规性校验。（KC-20261013-027）
- 幻觉/偏差归因三判据：概率命中 ≠ 理解、通用 ≠ 企业特色、概率最优 ≠ 业务正确——按判据定位偏差层级，决定补表示还是补验证。（KC-20261013-027）
- 边界：三阶段只抑制幻觉不消除；验证必须结合真实行动效果，不可纯模型自证。（KC-20261013-027）

### 8.6 嵌入方式选型

- 三法权衡：Prompt 嵌入 = 默认首选（低成本、快部署、快速迭代）；指令微调 = 仅专用模型场景（伤通用性）；数据增训 = 仅作补充（本体有漏洞时合成数据放大错误）。（KC-20261013-022）
- 微调/增训提案的前置证据：先跑 Prompt 嵌入基线并附其失败证据；例外场景 = 超高并发 + 规则极稳定的专用任务。（KC-20261013-022）
- 结构显性硬线：嵌入必须保留数值阈值与量化关系，规则按「条件–阈值–结论」三段结构注入；反模式 = 降维纯文本——把本体拍平成叙述文字，丢失结构与量化关系，本体退化为普通知识库（丧失可推理可审计性）。（KC-20261013-022）
- 结构显性与 Token 预算的张力靠切片化解：切片小则结构全（配合 §8.7）。（KC-20261013-022）

### 8.7 最小必要加载

- 只加载当前任务决策所必需的本体单元；盲目全量加载 = Token 浪费 + 关键信号稀释 + 无关规则互相冲突。（KC-20261013-021）
- 四种互补检索机制：SPARQL 精查（结构明确的关系/规则取用）/ 图向量模糊召回（意图模糊时候选定位）/ 记忆增强调用（高频任务捷径，成功调用模式沉淀入长期记忆）/ Skills 封装（稳定子任务复用接口）。（KC-20261013-021）
- 混合调用纪律：先模糊召回初筛候选，再精确查询验证逻辑关系——双通道防单通道误召；三工程原则 = 避免过度检索 / 精度效率权衡 / 混合调用。（KC-20261013-021）
- 基础设施前提：文档存储期可先落 Skills 封装 + 记忆增强两机制，SPARQL/图向量待图库就绪。（KC-20261013-021）
- 建设态最小化（§2.3）与运行态最小加载是同一纪律的两端：最小化的是加载粒度，不是建设质量。（KC-20261013-021，KC-20261013-008）

## 9. 全程总框架

### 9.1 五环联动（全生命周期）

- 五环：预处理（萃取+描述集+准入）→ 建模（生成+质检+把关+验收）→ 入库 → 平台 → 实施（点-线-面）。（KC-20261013-009）
- 环间严格输入契约：预处理产出 = 建模输入；建模产出过入库审查才成资产；资产经平台服务被实施消费——任何一环缺失都使下游退化为手工模式。（KC-20261013-009）
- 五环是框架不是等量齐观的建设清单：小切口项目可显式裁剪（如平台环不建、入库环简化为文档登记），裁剪决策须登记。（KC-20261013-009）
- 每环出口物即验收物：描述句集 / 本体模型 / 入库登记 / 服务接口 / 试点报告。（KC-20261013-009）

### 9.2 事实–事理–行动一体化（对象模型总纲）

- 三层定义：事实描述现实状态；事理解释因果逻辑与约束条件；行动将决策转化为可执行调用——使 Agent 在同一语义空间感知、推理、行动。（KC-20261013-001）
- 四要素原语：对象 / 关系 / 规则 / 行动；三层映射 = 事实层（对象定义→业务事实）、事理层（属性描述→规律逻辑）、行动层（关系定义→行动链路：如何触发+如何执行+如何反馈）。（KC-20261013-001）
- 组织原则：以高价值、高频、高风险的关键决策为中心反向组织数据、事理与行动闭环；拒绝泛化建设通用平台。（KC-20261013-001）
- 分层可信源硬要求：事实层 = 可信数据源；事理层 = 带来源、版本、适用范围与专家复核记录的专家知识——无来源、无复核记录的规则不得入模；行动层 = 可信执行依据。（KC-20261013-001）
- 动态闭环：事理模型接受事实数据持续校验，事实数据反向驱动事理更新；配「决策记录–结果反馈–模型优化」闭环。（KC-20261013-001）
- 术语纪律：本管线全程「本体」= 工程义（机器可理解的形式化业务语义框架），与哲学/个人认知义「本体」严禁混用。（KC-20261013-001，KC-20261013-019）

### 9.3 与既有数据资产的分工判据

- 四资产分工：实体建模（ERD）记录事实 know-what；本体定义事理 know-why/how；知识图谱承载实例（本体是图谱的语义骨架 Schema，图谱是本体的实例化数据载体）；数据湖留存历史——互补而非替代，反「替代论」（推倒重建）与「无用论」（已有图谱够了）。（KC-20261013-003）
- 档位选型一问：消费主体是「面向人的检索分析」→ 语义增强型图谱已够用；是「AI 自主决策」→ 才需要本体语义型；纯 BI 场景强上本体 = 过度工程。（KC-20261013-003）
- 本体库不是数据库：存 Schema 与事理规则，事实数据留源系统（映射不搬迁，§4.6）。（KC-20261013-003，KC-20261013-020）

### 9.4 立项粒度（一个任务一个本体）

- 本体立项的管理单元 = AI 任务：一个需 AI 替代人工执行的具体业务任务/决策对应一个本体；「一任务一本体」不是「一任务一库」——多个任务本体可共享公共层。（KC-20261013-017）
- 立项三基础：目标明确、效果可评估、闭环可控——核心解决业务问题，避免形式化本体。（KC-20261013-017，KC-20261013-019）
- 小切口起步、复用后再抽象：先从单一场景切入，数据可复用时再抽象为通用资产与标准化模型。（KC-20261013-017）
- 演进态区分：事理未建模 =「AI 业务数据」、已建模 =「AI 业务本体」——同一业务对象的两阶段，立项时登记当前所处阶段。（KC-20261013-017）
