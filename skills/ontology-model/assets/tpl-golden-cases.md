**归因纪律**：归因后才修，防止盲改——
- **模型缺陷** → 回 S3 修订本体（走 S4 重新质检，消耗博弈轮次记录）
- **用例错误** → 修正用例并重跑（预期结果与描述集原文冲突时，以描述集为准）
- **规则冲突** → 升级 G2 人工仲裁（规则间语义矛盾不是模型编译问题）
- **执行环境限制**（第四类）→ 根因在推理引擎能力边界（如 Pellet 限制⑩：facet 具名 datatype 实例层假不一致）时**修执行器不改本体/用例**；须先做削减实验定根因（逐构件对照+剥离对照，方法见 `references/reasoner-limits.md` §六），再登记引擎限制；本体若为合法 W3C 形态则零改动

## 5. 用例文件接口（golden-cases.json，schema 1.0）

本模板（md）是**人读层**；执行层为同 run 目录下的 `golden-cases.json`，由主会话按本模板登记内容转写（专家三元组 → JSON），执行器 `scripts/run_golden_cases.py` 消费。schema 校验：`python3 <skill根>/scripts/run_golden_cases.py --check golden-cases.json`（`<skill根>`=ontology-model skill 根目录，路径约定见 SKILL.md）。

| JSON 字段 | 对应本模板 | 说明 |
|---|---|---|
| `meta.schema_version` | — | 固定 `"1.0"` |
| `meta.scenario` / `meta.source` | 头部场景名 / 基线本体版本 | source 登记 ontology.ttl 版本号（如 v1.2.1） |
| `cases[].id` | 用例 #（G1/X1/P1…） | 全文件唯一 |
| `cases[].kind` | 用例来源分层 | `expert_seed`（专家种子，首选）/ `ai_edge`（边缘）/ `ai_negative`（异常）/ `ai_stress`（压力） |
| `cases[].seed` | §2.2/2.3「种子」列 | 可选；AI 扩展用例登记派生自哪条专家种子 |
| `cases[].gen` | 「生成方式」列 | 可选；变异/注入/枚举等生成手法 |
| `cases[].desc` | 用例描述 | 必填 |
| `cases[].ttl` | （执行细节，md 不呈现） | 虚构个体断言 Turtle 片段，复用本体文件 prefix 声明（以 `:` 前缀书写） |
| `cases[].expect` | 预期结果 | 断言列表：`["consistent"]` / `["inconsistent"]` / `["in_class", ind, cls]` / `["not_in_class", ind, cls]` / `["prop_value", s, prop, o]` / `["no_prop_value", s, prop, o]`（arity 由执行器 `ASSERT_ARITY` 硬校验） |
| `cases[].exempt` | §2.3 P2 类豁免项 | `true` = 登记不执行（如压力用例 MVP 豁免），不计入通过率分母 |

**纪律**：JSON 与 md 双载体登记同一用例集，md 为归因/闭环叙事层、JSON 为执行层；用例内容修订两处同步。skill 目录内不得存放真实业务用例（配例一律虚构中性）。

**敏感前置检查（desc/gen 字段）**：不仅 `ttl` 个体必须虚构，`desc`/`gen` 字段**同样过敏感扫描**——desc 通常直接引用专家黄金集的案例描述原文，最容易带入真实品牌名/机构名/人名。落盘前自检清单：① desc/gen/ttl 三字段全量过敏感模式——**泛化模式**（证件号/手机号等）内置于 `scripts/closeout_check.py`（BUILTIN_PATTERNS）；**真实机构名/人名/品牌名词表外置**，经 `closeout_check.py --patterns <词表文件>` 传入（TAB 分隔 ban/limit 规则），词表由部署方维护于受控目录、**永不进入 skill 资产**；② 命中即先脱敏为虚构语义名再写入；③ 敏感自查在**落盘前**执行而非落盘后修正（事后扫描是兜底不是门禁）。
